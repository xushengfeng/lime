# 对比实验结果

环境：Qwen3-0.6B-IQ4_XS，CPU 推理；输入统一为自然码双拼。时间为本机参考值，会随机器变化。

## 指标说明

**首选字符覆盖**（以前简称“字符准确率”）= 正确候选排在**第 1 位**时覆盖的汉字数 / 全文汉字数。

- 输入过程用正确文本作为 oracle 选择候选，和 `input_speed` 一样，只用来测候选排序；不是“自由选择首个候选后最终文本的 CER”。
- LIME 和词库 baseline 一次可能提交多个字，所以按候选实际覆盖的字数加权；字级 baseline 每个字一次查询。
- `查询首选率` 是“正确候选排第 1 的查询数 / 总查询数”，它按查询计，不按字数加权，所以多字候选的引擎会显得更低。

## 结论

- 加入雾凇词库后，baseline 明显变强：冰灯 53.85% → 59.40%，孔乙己 63.58% → 66.38%，一件小事 63.58% → 67.28%，论语 54.11% → 62.27%。
- 雾凇词库在四篇里都是最强的传统 baseline；Qwen token 词表在论语上接近它，其他文章略低。
- LIME 在冰灯和论语上领先约 10 到 11 个百分点；孔乙己上基本持平（+0.32）；一件小事上落后雾凇词库 5.31 个百分点。
- LIME 的 Top5 在所有文章上都最高，说明它的候选覆盖面更好，但首选命中不总是最好。现代叙事文本里，词库 + 在线调频已经很能打。

## 方法

- 用 `Intl.Segmenter` 把文章切成词段；每个中文词段整段转成自然码双拼后输入。
- 与 `input_speed` 一样，用正确文本作为 oracle 选择候选：记录正确候选的名次，提交后继续输入剩余拼音。
- 为了和 `input_speed` 一致，正确候选必须在当前词段内匹配；跨词段的长句补全不计入首选，这会低估 LIME 的长句能力。
- 雾凇词库：从 rime-ice 的 `base/ext/others` 合并，按权重取前 15 万条 2-8 汉字词，长词偏置 0.8，带在线词频和二元上下文。该文件不提交，运行 `pnpm bench:words` 生成。
- Qwen token 词表：从模型 GGUF 的 token 表导出 25,448 个汉字 token（其中约 1.6 万个多字词），用 `pinyin-pro` 注音，单字多音和字表兜底；同样长词偏置 0.8。该文件不提交，运行 `pnpm bench:tokens` 生成。
- baseline 没有分词器，只做“从当前位置开始的最长前缀词”候选；这对它偏不利，但符合“字表/词表 + 简单调频”的设定。

复现：

```shell
pnpm bench:ablation
pnpm bench:compare --article bench/articles/孔乙己.txt
pnpm bench:compare --article bench/articles/一件小事.txt --baseline-mode rime
pnpm bench:words      # 重新生成雾凇词表
pnpm bench:tokens     # 重新导出 Qwen token 表
```
